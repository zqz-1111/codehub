## 一、写在前面

1MiB分片的作用是将上传拆成较小请求，便于按片重发。分片全部发送完不代表文件一定可用，还要保证归属正确、片数齐全、顺序正确、大小准确，以及失败后能安全重试。

接管时发现：合并文件大小恒为0；总片数没有存储；分片请求可反复插入重复行；只按uploadId查询，没有会话归属；先删分片再保存元数据；同类调用protected事务方法可能绕过Spring代理；合并成功未投递代码索引；合并结果没有持久化回执。

这一轮围绕上述问题补齐流程，不以未经测量的“<150ms、零拷贝、消息零丢失”作为结果。

## 三、从上传到索引的实际流程

```text
WRITE/OWNER权限检查
  → uploadId参数检查
  → 获取共享会话锁（上传与合并使用同一把）
  → 显式启动数据库事务，锁定会话行
  → 上传：创建/校验归属与totalChunks，保存或替换分片
  → 合并：读取持久化回执，或校验完整分片后顺序读写临时文件
  → 上传最终对象，保存文件/Commit/合并回执，删除分片元数据
  → 提交数据库事务
  → 派发索引、清理分片对象、失效目录缓存
  → 释放会话锁
```

### 3.1 会话与分片各存什么

`upload_sessions`按uploadId存repoId、userId、totalChunks和状态；合并成功后记录文件ID、文件路径和文件名。uploadId全局唯一，不能被其他用户或仓库复用，即使另一个人也有该仓库写权限也不能接管这个上传会话。

`upload_parts`存每片序号、对象Key和字节数，并增加`UNIQUE(upload_id, chunk_index)`。同一个会话重复上传同一片，更新该行而非再插入一行。新分片对象使用独立UUID，避免先覆盖旧对象、随后数据库回滚造成内容丢失。

约定：序号从0开始；totalChunks在1至10000之间；每片1字节至1MiB。同一会话后续请求的totalChunks必须一致，已合并会话不再接收分片。

### 3.2 完整性和文件大小怎么校验

合并前检查：片数等于会话总片数，排序后索号恰为0至N-1，没有重复、缺失或越界；每片属于同一仓库/会话，状态为UPLOADING且有正字节数。读取对象时再次核对实际读出的字节数，超过记录长度立即拒绝。

最终sizeBytes等于按顺序读取的真实字节数之和，不再使用返回0的占位计算。此处验证字节数量与顺序；**尚未实现客户端整文件摘要比对，不能声称端到端内容校验和已通过**。

### 3.3 为什么使用临时文件

旧实现将所有分片拼进ByteArrayOutputStream，再转byte[]，整个文件驻留堆内存。现在每次使用8KiB缓冲区，将分片按顺序复制到临时文件，再从临时文件上传最终对象，finally中清理临时文件。

这是应用侧顺序I/O，仍有对象下载、本地磁盘写入和最终上传；没有使用MinIO服务端compose，不属于零拷贝。临时目录需要容纳整个文件，磁盘配额、超时和清理仍需在部署环境验证。

### 3.4 共享锁、数据库事务与回执分别解决什么

- **共享锁**：上传与合并都获取`lock:upload:{uploadId}`，避免合并过程中有请求替换分片。`tryLock(0, TimeUnit.SECONDS)`不等待，采用Redisson watchdog而不是固定30秒租期。
- **数据库行锁**：会话使用`SELECT ... FOR UPDATE`，在事务内检查和修改状态；数据库主键/唯一键作为约束。
- **显式事务**：在会话锁内部用TransactionTemplate开启REQUIRES_NEW事务，提交或回滚完成后才解锁；移除旧同类protected方法上的无效事务假设。
- **持久化回执**：MERGED会话在相同文件名和路径的重试中返回同一个文件ID，不重复创建文件和Commit；改目标则拒绝，原文件已删除则业务码410。

持久化回执只覆盖同一uploadId及目标，不是整个系统按文件内容去重。watchdog也不等于任何故障下绝对互斥，真实Redis/数据库故障场景仍需集成验证。

### 3.5 失败时保留什么、删除什么

| 情况 | 行为 |
|---|---|
| 分片元数据保存失败 | 数据库回滚，尝试删除本次新分片对象，保留旧对象 |
| 读取对象失败、分片长度不符 | 不保存最终文件，保留原分片以便重试 |
| 最终对象已上传，元数据事务随后回滚 | 尝试删除新最终对象；数据库分片记录应随事务回滚恢复 |
| 数据库提交成功 | 再删除临时分片对象；清理失败只记录日志，不把已提交合并伪装成失败 |
| 事务结果未知或进程直接崩溃 | 不能依赖回调完成清理，需要后续对账/孤儿对象清理 |

对象存储不参与MySQL事务，这里是回调补偿，不是跨系统原子事务。单元测试验证的是回调顺序与命令边界，数据库真实回滚仍待集成实测。

### 3.6 索引为什么提交后才投递

普通上传与合并调用同一派发器，在事务内准备内容，afterCommit中发送MQ，避免消费者在元数据提交前运行。MQ发送同步抛异常时尝试同步构建；索引构建单独使用REQUIRES_NEW，避免在afterCommit内复用已经提交的数据库事务。

当前自动索引范围：白名单文本扩展名、合法UTF-8、不含NUL字符、大小不超过1MiB。大文件或二进制文件仍可上传，但不自动索引；不能把“上传成功”解释成“任何文件都已建立向量索引”。

这个派发器不是事务Outbox。提交后进程退出、Broker异步nack或后续索引失败仍可能需要补偿；不能声称消息零丢失。MQ发送失败时的同步兜底还可能增加接口耗时。

## 四、普通上传防重的兼容修复

本轮复核发现，普通文件上传接口也使用`@Idempotent`。上一轮JSON指纹不能直接可靠序列化MultipartFile，会影响这个接口。这是上一轮遗漏，本次补齐：流式计算文件内容SHA-256，连同文件名和大小作为规范化参数，随后参与整体请求指纹；关闭自己的输入流，不消费后续独立读取的流。

新增回归测试确认相同文件内容得到相同Key、同名同长度但内容变化得到不同Key，以及指纹计算后仍能读取上传内容。通用文件流或任意对象仍不能不加约定直接套用。

## 五、数据库迁移与启动注意事项

**本轮未执行数据库迁移。新代码依赖新表/列，旧数据库未升级时不能直接启动验证新上传链路。**

- 新数据库：更新后的`codehub-server/sql/init.sql`已包含会话表、分片大小和唯一索引。
- 已有数据库：使用`codehub-server/sql/migrations/001_upload_sessions.sql`。
- 迁移前先备份并停止旧上传流量，单独运行重复片预检查。若返回任何行，停止后续DDL，先人工确认历史重复数据；本脚本不自动删除数据。
- 预检查通过后按顺序执行DDL。MySQL DDL隐式提交，不是可整体回滚的一次业务事务；不要对新库重复执行迁移文件。
- 历史未完成分片缺少可信归属和manifest，不自动推断或补造；使用新uploadId重新上传。
- 当前未添加过期会话/孤儿对象的定时清理，也未设置保留周期；后续按实际运行规模补充。
