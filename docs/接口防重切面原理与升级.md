# 接口防重切面：从重复点击到参数指纹与安全释放

> **速读版**：已把旧的 `toString().hashCode()` 升级为稳定 JSON + SHA-256；Redis 值改为每次请求独立的 UUID；异常时通过 Lua 比较 UUID 后再删除。新增 12 项单元测试全部通过。当前仍是 5 秒短时防重，不保证业务永远只执行一次。完整 Spring/Redis 集成测试本轮未运行。

> **同日后续更新**：普通文件上传接口也带防重注解，本次补齐MultipartFile内容指纹（流式SHA-256+文件名/大小），指纹测试5→6项，当前防重回归共13项。完整上传相关回归28项通过，详见 [[分片上传合并与索引可靠性升级]]。下方12项为首次升级时结果。

## 一、写在前面

用户连续点击两次“创建仓库”，或者网络慢导致客户端重发请求，如果后端照单全收，就可能重复写数据。前端禁用按钮只能改善体验，无法覆盖刷新页面、脚本请求或网络重试。

本项目用自定义注解 `@Idempotent` 标记接口，用 AOP（面向切面编程，即在业务方法执行前后统一插入逻辑）集中执行防重规则。学完应能说明请求怎么判重、Redis 为什么要原子占位，以及为什么它仍不等于业务幂等。

## 三、一次请求的完整流程

1. JWT 过滤器解析登录信息，将 `userId` 放入 HTTP 请求属性。
2. 请求进入带 `@Idempotent` 的 Controller 方法，AOP 环绕通知先执行。
3. 切面获取当前用户、完整方法签名和业务参数。ServletRequest/ServletResponse 是传输上下文，不参与指纹。
4. 参数序列化为 JSON，排序对象属性和 Map 键；保留数组、列表与参数顺序以及 null 位置，随后计算 SHA-256。
5. 拼出 Key：`idempotent:v2:{userId}:{完整方法签名}:{64字符摘要}`。
6. 生成 UUID 作为本次请求归属标识，一条 Redis 命令同时完成“不存在才写入”和设置过期时间。
7. 写入成功则执行业务；已有 Key 则拒绝。业务成功保留 Key 到自然过期；抛异常则比较归属后尝试释放。

### 3.1 注解与切面分别做什么

```java
// 注解只表达规则，实际拦截逻辑由 Spring AOP 执行。
@Idempotent(windowSeconds = 5)
@PostMapping
public Result<RepoVO> createRepo(...) { ... }
```

`@Around` 表示在目标方法前后执行；`joinPoint.proceed()` 表示真正调用目标方法。未拿到登录用户时，当前切面保留原行为，继续交给接口鉴权处理；创建仓库接口自身会返回未登录业务码。

### 3.2 参数指纹为什么要升级

旧逻辑拼接 `arg.toString()`，再调用 Java `String.hashCode()`。它输出32位整数，不适合直接当强请求指纹。本轮用旧 DTO 字符串复现：仓库名 `Aa` 和 `BB` 的参数字符串不同，但旧指纹同为 `-1756085914`，可能误拦合法请求。

新实现用 Jackson 稳定序列化和 JDK 自带 SHA-256。SHA-256 输出256位摘要，用64个十六进制字符展示。Map 插入顺序变化不应改变相同数据的指纹；参数顺序变化则必须区分。序列化失败直接报错，不生成共享的 `HASH_ERROR` 或空指纹。

稳定序列化不是通用业务等价判断：文本空格、列表顺序、数值表达、时间字段可能仍影响结果；本实现面向当前 JSON 风格的请求参数。摘要也不等于加密，低熵字段仍可能被猜测，不应把它宣传为保密机制。

### 3.3 原子占位为什么不能拆成两步

```java
// 对应 SET key requestToken NX EX 5 的语义。
Boolean acquired = redisTemplate.opsForValue()
        .setIfAbsent(key, requestToken, 5, TimeUnit.SECONDS);
```

如果先 GET 判断、再 SET 写入，两个并发请求可能都看到“不存在”。如果 SETNX 和 EXPIRE 分开执行，进程在中间退出可能遗留没有过期时间的标记。当前超时重载将占位与TTL一起提交。

- 返回 true：占位成功，执行业务。
- 返回 false：重复请求，抛出业务码429。
- 返回 null：结果未知，拒绝执行业务，抛出业务码503。
- Redis 调用抛异常：不降级放行业务；进入全局异常处理。

**当前 HTTP 状态仍为200，429/503 是 JSON 响应体的业务码。** 本轮未调整全局接口响应契约。

### 3.4 为什么异常释放要核对请求归属

```text
A 占位后执行超过5秒 → A的Key过期
B占用同一Key → B开始执行
A随后失败 → 如果直接DEL，就会误删B的标记
```

新的 Value 是每次请求独立生成的 UUID。释放用以下 Lua 脚本，让比较和删除在 Redis 内原子执行：

```lua
-- 只有当前Value仍然等于自己的UUID，才允许删除。
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

释放 Redis 出错时保留原始业务异常，把释放错误加入 suppressed 信息，标记等待TTL自然清理。成功后不释放，否则业务刚结束，第二次点击就能立刻进入。

## 四、方案选择与边界

| 方案 | 解决的问题 | 局限 |
|---|---|---|
| 前端按钮防抖 | 减少误点击 | 可绕过，刷新后状态丢失 |
| 本次Redis短窗口防重 | 拦截相同用户、接口、参数的短时重复提交 | 窗口过后允许再进；处理超时可能并发 |
| 分布式锁 | 保护临界区并发互斥 | 不是返回相同业务结果的协议，仍需考虑锁过期 |
| 业务幂等号/结果表/数据库唯一约束 | 防止重复落库、重复执行同一业务 | 需要结合业务身份、事务、状态机设计 |

**本轮选择**：升级当前短窗口防重，不把 Controller 注解改造成完整幂等平台。创建仓库是否唯一，仍应由业务规则与数据库约束兜底，先查询后插入不等于并发唯一保证。

## 五、踩坑避坑指南

- **SHA-256不会自动保证只执行一次**：它改善参数指纹，无法延长5秒窗口或确认数据库事务提交。
- **Lua比较删除不解决窗口过短**：能防A误删B，但不能防A、B在过期后同时执行。
- **异常不代表业务一定回滚**：当前兼容旧行为，所有从目标方法抛出的异常都会尝试释放。不能声称已按“可重试/未知结果”分类，不能直接复用到扣款等场景。
- **返回错误对象不等于抛异常**：切面只观察方法是否抛出，若方法正常返回错误Result，标记仍保留至过期。
- **鉴权未被替代**：切面未拿到用户时跳过防重；认证责任仍在接口和过滤器。
- **Key版本迁移**：新前缀为v2，旧Key不与新Key互通。部署时应停止旧实例接流量并等待至少旧窗口5秒后切换，避免混合版本同时处理同一请求。
- **不是所有参数都适合JSON指纹**：文件、流、自定义动态getter需要单独约定，不能简单忽略后让不同请求共用Key。

## 七、面试回答与全文总结

> 我通过自定义注解和Spring AOP统一处理重复提交，按用户、完整接口签名及稳定JSON的SHA-256指纹生成Key，用Redis原子占位和TTL实现5秒防重。每次占位保存独立UUID，异常时通过Lua比较归属后删除，避免旧请求过期后误删新请求的标记。该层负责短窗口防重，业务唯一性仍需结合数据库约束或幂等号。新增12项单元测试覆盖指纹、并发和异常边界，真实Redis集成验证尚待补齐。

记住三个区别：参数指纹负责识别请求；Redis占位负责窗口内拦截；数据库约束/业务幂等负责业务正确性。下一步先恢复基础设施验证这条链路，再处理分片合并与索引路径，不继续堆未经验证的简历数字。
